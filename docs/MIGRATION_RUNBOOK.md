# YapHub migration runbook - prepared, not executed

Migration, provider purchase and spending require a separate user decision. No replacement host has been provisioned.

1. Confirm the target's outbound IPv4 allocation and routing in writing, managed patch/reboot coverage, recurring price, backup retention, Python 3.13 support and provider contact path. Keep normal Discord restriction timing; migration is not a means to bypass an active block.
2. Pin the approved application revision and dependencies. Create a non-root service user, protected environment file, persistent data directory, one systemd bot service, firewall and TLS endpoint. Store credentials privately; never include them in logs or this runbook. Use /healthz for process liveness and /readyz for availability.
3. Use SQLite's backup API against the authoritative database while WAL is active. Verify integrity_check, checksum, schema and counts. Preserve profiles, active ownership, permits/blocks, telemetry, api_cooldowns, pending_joins, pending_cleanup and creation_intents. Never copy only the database file while ignoring WAL.
4. Transfer the verified backup securely to an isolated restore directory. Before connecting Discord, initialize the approved additive schema and compare profiles/ownership/cooldowns with the snapshot. Restore sent creation intents as unresolved. Confirm the retry deadline is unchanged. Validate the lifecycle against a local fake HTTP server; never start a second real bot for a restore test.
5. At the coordinated cutover window, stop the old worker. Verify the old process and replicas are stopped, then take a final verified backup including writes since rehearsal. Keep the old data/revision recoverable. Restore to the target, verify ownership and pending work again, then start exactly one replacement worker. Confirm HTTP liveness, preserved cooldown, and gateway readiness when eligible.
6. With coordinated SAL and YSL test users, observe lobby -> one room -> move -> panel -> leave -> cleanup. Confirm no duplicated rooms or dropped tracking. Observe 24 hours, recording queue wait and lifecycle timing. An infrastructure SUCCESS status does not replace these checks.
7. Roll back for duplicate creation, tracking loss or sustained healthy-state latency regression. Stop the new worker first. Take a final consistent snapshot with all recovery data/deadlines and restore it to the old service before restarting exactly one worker. Do not restore an earlier snapshot that forgets newer rooms or deadlines. Re-verify both guild lifecycles. An old application revision that ignores cooldowns must remain stopped until the restriction is cleared or use the last compatible recovery revision.

Rehearsal performed locally on 2026-10-12: an off-volume production backup matched SHA-256 b24b58cf91afc37e8afd6a1a4dcf6e0c6085543cf74c78becb5c21f903ab6988, passed SQLite integrity checking, and restored to an isolated database. Additive Release B initialization preserved all 26 profiles, 2 ownership records and the exact global retry deadline. No Discord connection was opened. This establishes storage rehearsal, not a migrated host or live acceptance.
